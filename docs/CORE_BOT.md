# Core bot v0.1

This is the first bootstrap slice of milestones 0–1, not completion of either milestone. Game modules live directly in the repository root and run without a build step.

## Local operation

On a fresh deployment, the bot discovers the room containing its initial owned spawn, derives that room's 9×9 sector interior, and persists `home` and `block` in `Memory.enclave`. No room names, spawn names, account IDs, or shard names need to be edited in game code. `core.config.js` contains only behavior/CPU tuning.

Discovery supports all four map quadrants and sector offsets, excluding the surrounding highway rooms. Multiple initial spawns in the same sector use a stable room-name ordering for the home label. With no spawn, initialization waits and retries; with initial spawns in multiple sectors and no saved territory, it reports `AMBIGUOUS_START_BLOCK` instead of guessing. Nonstandard room names such as `sim` and highway starts do not establish a sector.

Once saved, the territory does not change when more colonies appear, spawns are renamed or lost, or globals reset. The saved home and block must describe the same sector. A deliberate new empire with retained old memory needs an explicit memory transition; a new spawn elsewhere never silently replaces an existing territory.

The initial dev home was `W5N1`; after the user reset the world, the home is `W6N8`, inside `W1N1`–`W9N9`. These are observations of this world, not deployment configuration.

The user confirmed that this dev server contains one block. A read-only server inventory on November 21, 2026, at tick 1899 verified 121 rooms total: the 81-room interior plus 40 surrounding highway rooms (`W0`/`W10` or `N0`/`N10`). The interior contains 72 controller rooms, eight keeper rooms, and the controllerless center `W5N5`. This matches the configured ownership boundary.

At that observation, four other colonies occupied `W9N9`, `W9N1`, `W1N9`, and `W1N1`, each at RCL 2; home `W5N1` was RCL 1. An invader core existed in `W6N5`. These are dated development-world observations, not permanent assumptions or in-game scouting results. Administrative inspection does not populate bot intelligence; autonomous operations must still acquire their own vision. The current world has no additional rooms beyond this block and its highway ring.

**This repository is the active localhost Screeps script directory. Editing root JavaScript files changes the running bot when the client synchronizes them.** Stage and validate coordinated changes outside the watched directory before copying them in. For initial installation, copy dependency modules first and `main.js` last. Future incompatible updates need a deliberate activation/rollback procedure; replacing several live files is not an atomic deployment.

The initial spawn is already placed. The bot discovers owned rooms within its boundary, bootstraps with generalists, then adds source miners and haulers as room capacity reaches 550 energy. Generalists become controller consumers, with one builder while sites exist. Home workers stay in their home room; explicitly assigned scouts and remote crews use bounded inter-room travel. Unknown or unrelated creeps are not adopted or given orders.

At RCL 2, the bootstrap planner starts extensions. At RCL 3, it prioritizes a tower before remaining extensions. It searches terrain incrementally, preserves source/controller working space, and checks connectivity before requesting a site. Existing towers attack visible hostiles. Established building positions are saved and missing buildings are reconstructed on their saved tiles before new expansion sites are considered. At RCL 4, storage is placed before additional extensions. RCL 4 also starts a terrain-aware wall/rampart perimeter and budgeted repairs; RCL 5 adds storage-to-controller links. Threat-sized defense, home evacuation, safe mode, roads, containers, and industry operation remain future work. Full RCL 8 building capacity is reserved before adopting the new perimeter.

## Console commands

- `status()` — CPU sample summary, schema, home, block, and recent alerts.
- `roomReport('W5N1')` — staffing, energy, spawn decision, placement status, and observation age.
- `territoryReport()` — all 81 rooms with observed ownership and vision age; unknown rooms remain unknown.
- `explain('creep-name')` — the worker's assignment, current task, and last action return code. A room name returns its colony report.

Summaries print every 100 ticks. Repeated errors are throttled, and history is capped at 50 alert keys and 100 CPU samples. These samples are diagnostic measurements, not verified live CPU capacity or the planned 1,000-tick trends. `roomReport(home).expansion` reports the remote operation, its current gate, resolved delivered energy, and total energy spent spawning its crews.

`Memory.enclave` schema 2 stores `home`, `block`, `colonies`, `intel`, `alerts`, `samples`, and `sequence`. Schema 1 migrates in place by locating an owned spawn within its saved block, or a saved colony if the spawn was lost. The migration validates the sector before changing any fields and preserves the block, workforce, plans, metrics, and sequence. If several legacy candidates exist, the first sorted spawn room (then saved colony) becomes the home label; schema 1 did not record historical spawn order. Worker memory stores `role`, `home`, `working`, `sourceId`, optional plain-coordinate `miningSpot`, `task`, `lastAction`, and `motion`. Native movement may also use its own creep-memory path cache. Missing vision preserves the last observation with its timestamp. Global caches are disposable. Each colony may also hold `layout: {version: 1, buildings: [{type, x, y}]}`; this additive schema-2 field stores established positions independently of structure IDs.

For compatible live rollout, install the additive territory helpers first, then the schema-2 memory reader/migration, then reporting, and remove the old location configuration last. Verify each dependent phase has synchronized. The old schema-1-only reader cannot read migrated memory; a rollback must retain the schema-2 reader and territory helpers or use a separately validated reverse migration. Never overwrite live progress with a stale memory snapshot as an incidental rollback.

Below specialist capacity, the bootstrap workforce target remains two generalists per source, with a floor of two and cap of six. Loss of viable generalists triggers affordable 200-energy recovery bodies (`WORK`, `CARRY`, `MOVE`). Once capacity reaches 550, demand uses source energy capacity / regeneration interval / harvest power: an ordinary owned source requires five WORK parts. Its miner stays at the source; haulers collect dropped energy or container stores.

Harvesters reserve distinct source-adjacent tiles, including while traveling. Walls, blocking structures, disconnected paths, occupied tiles, and routes through stationary harvesters are excluded. An incumbent retains its tile; a displaced miner can use another source with a free slot and unmet mining demand. Bootstrap gatherers use the same slot allocator. If no useful slot is free, a replacement retains its source and approaches range two to wait for takeover. Exhaustion alone does not move a dedicated miner away from its source. Assignments rebuild from current vision and saved coordinates after global resets; there is no room-specific layout.

`roomReport(home).miningSources` reports usable `slots`, `assigned` harvesters (including travelers/pending miners with reservations), and `waiting` miners per source. The fresh-world home was observed at `W6N8` after the user reset; its sources have three and one usable slots. See the [mining-slot validation](validation/2026-11-21-mining-slots.md).

Transport demand uses the longest complete source-to-spawn/controller route, terrain-dependent loaded travel, empty return travel, and four handling ticks. Haulers use equal CARRY/MOVE parts. Generalist WORK demand deducts estimated specialist replacement upkeep from income; bodies scale up to three WORK/CARRY/MOVE units. These are initial sizing estimates, not proof of delivered throughput. Source piles can still accumulate through transport delays and dropped energy decays. Containers, roads, and measured delivery-trip sizing remain future work.

In a fed colony, generalists spend partial deliveries immediately and stay at distinct controller stations; only the final generalist builds while sites exist. Haulers refill spawns/extensions first, then owned towers to their actual energy capacity, before supplying consumers. Generalists use the same full-tower target when providing fallback delivery; existing downgrade protection and the dedicated consumer role remain in place. Delivery paths block individual reserved stations and current nearby worker tiles; they do not block a blanket square around the controller. Upgraders can use the full three-tile upgrade range, with station choices ranked by actual approach-path length. Each chosen station preserves a supply lane that cannot become another station. Path reuse is disabled near the controller. A carrier with an open exit can transit normally; an enclosed carrier, or one occupying a reserved station, gets a coordinated escape step/swap toward reachable space outside upgrade range. Ordinary roles cannot overwrite either participant’s recovery movement that tick. If a mobile friendly worker and connected exit cannot be found, recovery waits with `WAIT_CONTROLLER_EXIT`. This is controller-specific recovery, not a general room traffic solver.

`roomReport(home).economy` exposes actual event-based harvest and upgrade energy, the latest complete 300-tick window, and unused source energy on regeneration. `staffing` compares active part totals with targets. At tick 26387 the current dev colony had reached RCL 3; a completed window recorded 6,000 harvested energy and 2,742 upgrade energy. This is observed progression in the existing world, not a fresh-seed milestone run. See the [economy validation record](validation/2026-11-21-economy-throughput.md).

## Building reconstruction

The bot adopts existing owned structures and owned construction sites, plus neutral roads, containers, and walls in its owned room. New planner sites are saved immediately when accepted. Layout observation runs even when low CPU or hostiles defer construction; missing vision never deletes saved positions. Saved entries are deduplicated by type and tile and survive serialization/global resets.

On scheduled planning ticks, reconstruction precedes new placements, with spawn, tower, then extension priority. A matching building or site satisfies that position, so rebuilding is not duplicated. Site caps, threats, room limits, and CPU gates remain in force. The engine checks tile legality; a rejected request leaves the saved position intact and reports `REBUILD_FAILED_*`. A current structure-count/RCL limit reports `REBUILD_LIMIT_*`. Pending reconstruction takes precedence over new expansion, including when blocked; there is no automatic relocation or demolition.

The original spawn can receive a replacement site even when no spawn remains. Surviving harvesters provide mining-access origins during that interval. Completing reconstruction still requires enough surviving workers, energy, and lifetime; this does not recover a completely extinct colony automatically.

Tracking starts with the layout present at activation. It cannot infer positions destroyed before they were recorded, or recover plans after Memory is deliberately cleared. Removing a saved construction site is treated as missing infrastructure and recreates it; intentional redesign requires an explicit layout revision. Walls and ramparts are the exception once a version-2 perimeter is adopted or its replacement has matching explicit approval: only matching barrier types and positions in that plan are reconstructed. Manually deleting an old/off-plan wall or rampart leaves it removed, including across global resets. A wall at a planned rampart passage is not recreated as a wall; the perimeter planner supplies the planned rampart. Other building reconstruction is unchanged. See the [reconstruction validation](validation/2026-11-21-building-reconstruction.md).

## Scouting, remote mining, and storage

This is the first slice of milestones 2–3, not completion of those milestones. `territoryReport()` exposes observations only; administrative inspection never seeds scout intelligence. New memory is additive to schema 2. Each colony may hold `expansion: {reason, capacityReason, remote, remotes, capacityChanged}`; `remote` remains a compatibility alias for the first operation, restored after JSON serialization; its remote record persists the chosen room/source, route estimate, hauling demand, state, resolved delivered total, gross spawn spending, and bounded actor IDs for event attribution. Traveler creep memory adds `targetRoom`, a scout destination timestamp, and per-room retry deadlines. Resetting JavaScript globals preserves these assignments.

Local haulers retain spawn/extensions → tower priority, then refill low worker buffers and bank remaining cargo. With usable owned storage, an upgrader requests energy below 15 ticks of active WORK consumption and receives up to 30 ticks, capped by carry capacity. This gap prevents continuous small worker top-ups from starving storage. Builders and urgent controller protection retain full refills; without usable storage, the former full-consumer policy remains. These thresholds live in `core.config.js`. During a source-output gap, an empty hauler can withdraw from owned storage for actual outstanding home demand, without withdrawing merely to top up buffered workers. One local distributor withdraws batches from storage and supplies spawn/extensions, towers, and low worker buffers even while source drops remain available. It retains spare cargo between refills. Source carriers continue collecting and bank surplus; the distributor uses the same delivery reservations and controller-formation traffic protections. Its body scales to six CARRY/MOVE pairs, and spawning/pending replacements are counted. Critical source mining/first transport and emergency workers keep priority; distribution precedes additional controller consumers and remote spending. Storage participates in established-layout reconstruction.

After home staffing is satisfied, one 50-energy MOVE scout surveys the block. Tower energy deficits, urgent controller downgrade, missing planned spawns/towers, and low CPU defer scout spawning. Ordinary construction, including storage, does not suppress scout replacement. New remote crews wait for ordinary established construction; already productive operations keep replacements through link and barrier construction. Missing spawns/towers still defer remote spending. Scouts prefer unseen nearby rooms, then old observations. Routes never cross the saved boundary, even as an intermediate step. Known foreign ownership/reservations, keeper lairs, invader cores, and recent hostile sightings prevent entry. New threats cause retreat; disconnected rooms remain unknown and are retried later. Intelligence records source slots, sources' observed capacities, controller/reservation facts, mineral, exits, and active hostile parts.

An eligible adjacent neutral controller room can supply one remote source. With the RCL 4 budget active, admitting another room requires storage above the reserve floor plus 2,000 energy; crew replacements require at least 2,000 stored energy. The budget selects one to four adjacent rooms; each keeps a single source operation. The planner requires an observation no older than 500 ticks, an available source slot, no foreign ownership/reservation or NPC threat, and a complete two-room terrain path costing at most 200 from storage, predicted net income of at least two energy/tick after crew replacement and reservation, and enough spawn headroom. Hauling is sized conservatively for a fully reserved source at 10 energy/tick and the estimated round trip, with bodies capped at 12 CARRY/MOVE pairs. The bot commissions a collector first, then a five-WORK/five-MOVE drop miner, the remaining transport capacity, and a two-CLAIM/two-MOVE reserver when 1,300 spawn capacity permits it. The last increases reservation time faster than natural decay. Existing active crews continue when the storage reserve dips; new optional crew spending waits. Collectors wait near home storage until their producer reaches the source, avoiding early congestion at narrow source entrances. Loss of home ownership stops remote work with an explicit task reason. Local replacement requests always win arbitration. There is still just one room spawn coordinator; optional route surveys run afterward in their own fault boundary.

Every visible-room observation refreshes safety. Threats, stale vision, lost storage, unusable source slots, or a failed periodic route check pause the operation. Crews retreat and loaded haulers try to return their cargo to home storage. Fresh safe observations after the 1,500-tick threat cooldown permit resumption. Paused operations retain their identity; automatic alternate-source selection after a long pause is future work. Scouts can restore stale vision. No keeper mining, guards, remote containers, roads, claiming, or expansion of the saved block is enabled.

`remote.delivered` counts resolved energy transfer events into home storage, including a previous-tick actor that has since died. It does not count accepted transfer intents as successful deliveries. `remote.spawnEnergy` is cumulative gross crew spawning cost; these two counters are diagnostic, not amortized profit or proof of sustainable remote throughput. Initial live delivery has now been observed; sustained reservation, raid recovery, and replacement-cycle validation remain. The [expansion validation record](validation/2026-11-21-scouting-remotes-storage.md) distinguishes deterministic test coverage from observed engine behavior.

Mechanics checked against the [official Screeps API](https://docs.screeps.com/api/) on November 21, 2026: `Game.map.findRoute` supports Infinity route exclusion; PathFinder callbacks reject unauthorized rooms; reserveController uses adjacent CLAIM parts; storage unlocks at RCL 4; room event logs report completed transfers. The local observer is development tooling, not a game dependency.

The [storage distribution validation](validation/2026-11-21-storage-distribution.md) records the later deposit fix, dedicated distributor, and initial live remote deliveries. It supersedes the initial rollout's pending-storage observation without declaring the wider milestones complete.


## RCL 4 perimeter and RCL 5 links

`planning.envelope` protects the viable room interior, including source/controller working areas, rather than drawing a tight boundary around current buildings. The eight-neighbor, node-split minimum cut minimizes barrier tiles for that protected interior. Natural terrain supplies the remaining boundary. `planning.cut` advances at most eight augmentations per call under the CPU guard; a global reset discards the search graph and recomputes it. The policy prioritizes retaining the broad interior, then minimizing its barrier count; it does not claim a global optimum over every possible area-versus-maintenance tradeoff.

Rampart passages preserve friendly routes to infrastructure, resources, and every reachable exit within four steps of the unobstructed baseline. Reserved travel cells stay clear of future buildings. Before adoption, `planning.mature` reserves the full RCL 8 structure allowance, including 60 extensions, ten labs with two valid reaction inputs, six links, three spawns, and the mineral extractor. Candidate structures must preserve interaction and exit connectivity. The persisted draft resumes across serialized Memory and global resets. Existing labs that need redesign or insufficient terrain capacity produce explicit review states instead of silently reducing capacity. Reserved future links and industry buildings are capacity reservations, not implemented industry operations.

**New ordinary buildings must be inside the protected area, at least three Chebyshev tiles from every planned barrier and five tiles from room edges.** These are configurable bot planning margins, not claims about the game's construction rules. `buildingWallClearance` and `buildingExitClearance` live in `core.config`. Both reservation and construction enforce them. `mature.policyKey` invalidates outdated footprints and `buildingArea` records the inset area. Existing structures remain established reconstruction positions. The fixed mineral must satisfy the policy or reservation reports `FIXED_MINERAL_CLEARANCE_REQUIRED` for review.

Plans persist as `perimeter: {version, status, plannedAt, tiles, inside, gates, cutSize, routes, legacyWalls}`. Fresh rooms adopt a validated version-2 plan automatically. Existing version-1 rooms retain their enclosure and produce `perimeterProposal` with `MIGRATION_REVIEW`; no demolition occurs without approval. Ordinary new expansion pauses during that review while reconstruction continues. Site caps, threat checks, CPU limits, and reserves remain in force. `ENCLOSED` means planned barriers exist, not that the room has demonstrated resistance to a raid.

`approvePerimeter(roomName, plannedAt)` records explicit approval of the currently reviewed replacement. `planning.migration` first builds every outer barrier to at least 5,000 hits. It then converts approved wall passages only with a funded engineer already within build range, and waits for each replacement rampart to reach 5,000 hits. Only then does it retire approved old interior walls, one request per tick. Actual later vision confirms completion; an accepted intent is insufficient. Hostiles, ownership loss, inadequate CPU, weak outer barriers, missing engineers, site backlog, or failed engine requests defer the relevant step. Automatic migration removes reconstruction records only after accepted approved removals. Off-plan wall and rampart records are excluded from reconstruction as soon as the replacement is approved, so player deletions are respected before automatic retirement is ready. Replacing a wall with a rampart necessarily creates a short opening while the gate is constructed; conversion is restricted to a peaceful room with an engineer present. This is an explicitly authorized migration, not general automatic demolition.

At RCL 5, `planning.links` places a hub near storage and a receiver near the controller, checks both obstacles together for access, and remembers their roles in `links: {hub, controller, status}`. RCL 5 allows two links. The hub sends at most its energy and the receiver's free capacity when cooldown is zero; the engine applies transfer loss. `links.transfer` is the last accepted/failed **intent**, not proof of delivered energy. Haulers/distributors refill spawn/extensions and towers before the hub. Controller stations prefer receiver-adjacent tiles without closing delivery lanes. Candidate formations must preserve existing infrastructure/source/exit access within four steps of its baseline distance from the spawn; this prevents a receiver formation from closing the direct colony transit corridor. Empty workers approach the receiver and withdraw with shared amount reservations, then return to their working stations. Carrier delivery remains available. `movement.yield` lets an adjacent-access carrier ask a ranged worker to step aside or swap while remaining in work range. Tick-local reservations prevent a later worker intent from overriding that yield; a short saved cooldown prevents immediate return to the obstructing tile. Engineers and returning remote haulers share local access protections. Engineers additionally validate that a path reaches the requested work range before moving. An incomplete 1,500-operation search retries with a 10,000-operation limit; if needed, a further retry permits vacant station reservations. A final geometric retry ignores temporary creep occupancy and station reservations while retaining room borders and structure obstacles. Before each step, engineers check actual occupancy of the next tile: they proceed when clear, ask a ranged worker to yield when possible, or wait locally. A distant temporary blockage therefore does not stop room-wide travel. This avoids a false barrier formed by reserved stations plus displaced upgraders. Incomplete retries return `ERR_NO_PATH` without moving toward a partial endpoint. Complete paths are cached briefly in disposable globals; fatigue skips search and resets regenerate paths. `moveReason` distinguishes `FOLLOW_ROUTE`, `WAIT_TRAFFIC`, `YIELD_TRAFFIC`, `FATIGUE`, `IN_RANGE`, and `NO_COMPLETE_ROUTE`; this describes the latest movement request, not necessarily the current task. Other roles retain their existing movement policy. Source links at higher RCLs remain future work. [Official link mechanics](https://docs.screeps.com/api/#StructureLink).

## Defense spending and remote capacity

`economy.budget` separates desired defense effort from currently funded effort. `defense.policy` provides the shared goals for budgets and repairs. The default long-term targets and reserves are:

| RCL | Barrier goal | Reserve floor | Reserve target | Desired engineer WORK cap |
| --- | ---: | ---: | ---: | ---: |
| 4 | 100,000 | 20,000 | 75,000 | 5 |
| 5 | 1,000,000 | 50,000 | 150,000 | 15 |
| 6 | 5,000,000 | 100,000 | 250,000 | 25 |
| 7 | 20,000,000 | 150,000 | 350,000 | 40 |
| 8 | Actual structure maximum | 200,000 | 500,000 | 60 |

The engine's standard maximum at RCL 8 is 300 million hits for walls and ramparts; runtime goals honor each existing structure's actual `hitsMax`. Lower levels also clamp to `hitsMax`. The reserve floor additionally respects room energy capacity × 10; the target adds up to 50,000 for queued construction. Large wall-hit goals do not add their entire repair bill to the reserve target. Surplus above target is available over a 5,000-tick draw horizon, while deficits request recovery over the same horizon. `stockDeltaPerTick` reports measured storage change over 500 ticks.

Engineers lift deficient barriers through shared milestones: 5k, 25k, 100k, 250k, 500k, 1M, 2M, 5M, 10M, 20M, 50M, 100M, 200M, then 300M (and actual maximum if different). Completed low-target barriers do not pin the whole colony to a lower tier. Fragile ramparts retain emergency priority. Approved retiring walls are maintained only to the migration minimum while present; off-plan barriers do not attract ordinary fortification spending. Manual removal policy remains unchanged.

Funding accounts for controller demand, local replacements, observed harvested energy when available, active remote delivery minus replacement costs, rampart decay, engineer replacements, and tower firing during hostiles. `desiredEngineerWork` drives remote demand; `engineerWork` is limited by income and controlled reserve draw. Routine withdrawal slots are assigned to existing engineers by name in whole-creep WORK units; a selected final crew can exceed the numerical WORK allowance by the remainder of its body. Other existing engineers pause routine refills, while already carried energy may finish work. Fragile ramparts and the assigned migration gate engineer retain emergency priority. All ordinary withdrawals still stop at the reserve floor.

`remoteDemand`, `activeRemoteIncome`, and `remoteShortfall` expose the desired income and the unfunded portion; a high target is not proof that enough safe sources exist. Zero measured delivery is no longer reported as positive profit. Newly admitted operations have no funding credit until a measured delivery window is available; predicted income is used for admission and demand sizing only. Remote selection predicts capacity after reservation when the room can afford a reserver, or observed source output otherwise. Candidate diagnostics record route cost, predicted net income, spawn load, and rejection/admission reason. Total estimated home plus remote replacement load must stay below 80% of available spawn time. Existing routes that become uneconomic pause. Current scope remains one source per safe adjacent room, at most four rooms, inside the saved block; no hostile, keeper, or foreign-room mining is enabled.

Scouts use complete, bounded static paths between the current and next authorized room, with a short disposable cache. This prevents an incomplete route from trapping the survey at a cul-de-sac and starving remote admission of fresh observations. Static scout routes do not implement general traffic negotiation. Search work is bounded at 20,000 operations and room-route permission remains unchanged.

Rampart decay is budgeted per actual/planned gate position independently of target strength. Towers still attack first and only perform emergency rampart repair in peacetime above 500 stored energy. Higher wall goals buy response time; boost-aware combat, dedicated defenders, and automatic safe mode are still outside this slice. [Official defense mechanics](https://docs.screeps.com/defense.html).

`economy.engineer` is a managed local role, included in snapshots, memory cleanup, dispatch, formation-aware movement/escape and replacement accounting. New engineer bodies have up to five WORK/CARRY/MOVE/MOVE units (250 energy per unit) for loaded movement on plains without a fatigue pause; total requested engineering WORK follows the level-dependent cap and funding budget. Critical local transport/mining and the distributor precede engineering; recovery generalists retain the existing emergency path. Cargo already withdrawn may finish work when storage subsequently crosses the floor.

Remote demand estimates controller spending, engineering work, rampart upkeep, reserve recovery and local replacement costs. A remote's net estimate deducts mining/hauling and reservation replacement costs from measured resolved delivery rate when available, otherwise an initial 10-energy/tick gross estimate. Rates are bounded estimates, not demonstrated profit after combat or infrastructure costs. Fleet size remains capped at four adjacent rooms, one source per room, and changes no faster than once per 1,000 ticks. An unmet budget prioritizes stale eligible neighboring surveys before the wider block. `expansion.capacityReason` retains admission failures between expensive survey ticks. Hostile/NPC rooms, stale intel, incomplete routes and routes above the cost limit or below the net-income floor remain ineligible even when demand is high.

Surplus operations retire without suicide: no replacement crews, and loaded haulers return cargo. Each operation separately owns delivered energy, spawn spending, actor attribution and a delivery sample. Legacy singleton state migrates additively; roles select their operation by target room and source ID. Existing profitable work continues during lengthy barricade construction. The implementation supplies economic demand and safe adjacent admission; it does not guarantee that enough safe rooms exist to fund every desired expense.
